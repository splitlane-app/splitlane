# SplitLane, этап 1: спецификация

Дата: 2026-11-13. Статус: на согласовании.

## 1. Что делаем и зачем

SplitLane — приложение для Windows 10/11, в котором пользователь перетаскиванием раскладывает программы по двум дорожкам: «Через VPN» и «Напрямую». Причина: часть ресурсов через VPN работает медленно или не работает вовсе, а встроенного деления по программам у многих VPN нет.

Продукт задуман как публичный, бесплатный, с открытым кодом (GPL-3.0-or-later), для любых VPN. Работа разбита на этапы (раздел 14). Этот документ описывает **этап 1**: рабочий инструмент на одном ПК с подключением через Tailscale и exit node.

Критерии успеха этапа 1:

1. Пользователь входит в Tailscale из приложения, выбирает exit node и включает деление без ручной правки файлов.
2. Программа, перетащенная в другую дорожку, начинает выходить в сеть с адреса этой дорожки не позже чем через 3 секунды после получения `lanes.set` служебным процессом, без перезапуска приложения и ядра.
3. Пока ядро работает, соединения программ дорожки «Через VPN» не уходят напрямую без явного действия пользователя. Исключения перечислены в разделе 10.
4. После выключения, выхода из приложения, падения ядра или служебного процесса и после перезагрузки компьютер возвращается к прежнему состоянию VPN: если до включения в приложении Tailscale был выбран exit node, он снова выбран — сразу при штатном выключении, а после сбоя служебного процесса или перезагрузки при следующем старте служебного процесса (5.7).
5. Окно работает без прав администратора; программу можно перетащить в окно из Проводника.

## 2. Объём этапа 1

Входит:

- Доска с двумя дорожками, закрепление программ, выбор основной дорожки, поиск.
- Добавление программ: из списка «Сейчас в сети», из списка установленных, файлом с диска, перетаскиванием из Проводника.
- Живая активность: скорость по программам и дорожкам, соединения в карточке программы.
- Коннектор Tailscale: вход, выбор exit node, согласование с установленным клиентом Tailscale.
- Служебный процесс с правами администратора, запуск через планировщик задач.
- Значок в трее, автозапуск, экраны состояний.
- Интерфейс на русском; все тексты в словаре.

Не входит: установщик и служба Windows, обновления, подпись кода, ключи и подписки (VLESS и другие), файлы WireGuard и OpenVPN, режим «адаптер чужого VPN», раздельный DNS по дорожкам, правила для сайтов, английский интерфейс, macOS и Linux.

## 3. Термины

- **Дорожка** — один из двух маршрутов: `vpn` или `direct`.
- **Основная дорожка** — дорожка, по которой идут все незакреплённые программы.
- **Закреплённая программа** — программа с сохранённым правилом; остаётся в своей дорожке при смене основной.
- **Ядро** — sing-box, сторонний сетевой движок; запускается как отдельный процесс без изменений.
- **Служебный процесс** — `splitlane-helper.exe`, единственная часть SplitLane с правами администратора.
- **Встроенный узел** — узел Tailscale внутри ядра; отдельное устройство в сети пользователя.
- **Системный Tailscale** — официальный клиент Tailscale, если он установлен.
- **Локальный API ядра** (Clash API) — интерфейс ядра `clash_api`: список соединений, их закрытие, переключение режима ядра. Слова «локальный API» и «API ядра» дальше означают его.
- **Служба API** — отдельная служба ядра `api` (появилась в версии 1.14): состояние встроенного узла, ссылка для входа, список узлов, вид соединения с exit node. У неё свой порт и свой секрет.

## 4. Архитектура

```
Окно (Electron, без прав администратора)
   │  именованный канал, сообщения JSON
Служебный процесс (Go, права администратора)
   │  запуск процесса, локальный API ядра
Ядро sing-box 1.14.4 (без изменений)
   ├─ виртуальный адаптер: перехват трафика
   ├─ правила по процессам в файлах, перечитываются на лету
   └─ встроенный узел Tailscale → exit node
```

Правила разделения ответственности:

- Окно ничего не знает о ядре и его конфиге. Оно отправляет служебному процессу намерения («включить», «разложить программы») и показывает его состояние.
- Служебный процесс сам собирает конфиг ядра из проверенных данных, запускает ядро, переключает системный Tailscale и следит за связью. Он не принимает от окна пути к исполняемым файлам для запуска и готовые конфиги.
- Ядро скрыто за интерфейсом драйвера (`CoreDriver`): собрать конфиг, применить дорожки, получить соединения, закрыть соединения, состояние коннектора. На этапе 1 драйвер один, для sing-box. Интерфейс нужен, чтобы на этапе 3 добавить mihomo без переделки остального.

### 4.1. Состав репозитория

- `app/` — окно: Electron, React, TypeScript, сборка electron-vite, менеджер пакетов pnpm.
- `helper/` — служебный процесс: модуль Go.
- `scripts/` — получение ядра с проверкой контрольной суммы, сценарная проверка.
- `docs/` — спецификации и планы.

Бинарные файлы ядра в git не хранятся. Скрипт скачивает архив `sing-box-1.14.4-windows-amd64.zip` с GitHub и сверяет SHA-256 с зафиксированным в репозитории значением.

Первая задача плана создаёт репозиторий git. В `.gitignore` с первого коммита: `spike/`, `.superpowers/`, каталог скачанного ядра, каталог данных режима разработки, каталоги сборки, `node_modules/`. Папка `spike/` содержит ключ узла Tailscale, секрет API и настоящие адреса и не должна попасть в историю; перед первым коммитом вывод `git status` проверяется на отсутствие этих путей. В корне лежат `LICENSE` (текст GPL-3.0), `README.md` и `THIRD-PARTY.md` (ядро: версия, лицензия, ссылка на исходный код тега v1.14.4).

### 4.2. Размещение на диске

| Путь | Содержимое | Кто может писать |
|---|---|---|
| `%ProgramFiles%\SplitLane\` | служебный процесс, ядро, тексты лицензий | администраторы |
| `%ProgramData%\SplitLane\` | состояние, журнал возврата (5.7), конфиг ядра, файлы правил, состояние встроенного узла, журналы | администраторы и SYSTEM |
| `%ProgramData%\SplitLane\export\` | архивы журналов (`diagnostics.export`) | администраторы и SYSTEM; пользователь, выполнивший настройку, может только читать |
| `%AppData%\SplitLane\` | настройки окна, кэш значков | пользователь |

Каталог `%ProgramData%\SplitLane\` создаётся с явным списком доступа без наследования; обычный пользователь не имеет к нему доступа. В нём лежит ключ встроенного узла. Исключение — подкаталог `export\`: в него служебный процесс кладёт архивы журналов, и пользователь, чей SID записан при настройке, может их читать. Окно копирует архив оттуда в место, которое пользователь выбрал в диалоге сохранения.

### 4.3. Первая настройка и запуск

1. Окно при старте проверяет, отвечает ли канал служебного процесса. Если нет и задача планировщика не зарегистрирована, показывает экран «Настройка» с одной кнопкой. Если канал существует, но отказывает в доступе (SplitLane настроен другим пользователем этого компьютера), окно вместо экрана «Настройка» сообщает об этом.
2. По кнопке окно запускает `splitlane-helper.exe install --user-sid <SID>` с запросом UAC. Команда сверяет SHA-256 файла ядра со значением, зашитым в служебный процесс, и при несовпадении отказывает. Затем она копирует служебный процесс и ядро в `%ProgramFiles%\SplitLane\`, создаёт `%ProgramData%\SplitLane\`, записывает SID пользователя и регистрирует задачу планировщика `SplitLane Helper` из XML. Задача выполняется от имени этого пользователя в его сеансе, с наивысшими правами; запуск по требованию разрешён; есть триггер «при входе этого пользователя»; без ограничения по времени, без условий по питанию, повторный запуск игнорируется. Служебный процесс собран без окна консоли и запускает ядро без окна. Если UAC пройден под другой учётной записью (пользователь повышенного процесса не совпадает с `--user-sid`), `install` отказывает: на учётной записи без прав администратора задача не получит повышенных прав, этап 1 такую учётную запись не поддерживает. При запуске по триггеру служебный процесс выполняет возврат по журналу (5.7); если после этого включать деление не нужно и за 60 секунд не подключилось окно, он завершается.
3. В дальнейшем окно запускает задачу командой `schtasks /run` без UAC и подключается к каналу. Если канал пропал во время работы, окно запускает задачу снова (раздел 10).
4. `splitlane-helper.exe uninstall` (с UAC) действует по порядку. Если канал отвечает, команда отправляет `helper.shutdown` и ждёт завершения служебного процесса; пока выключение 5.4 не подтвердило возврат системного exit node, удаление не продолжается, команда сообщает причину. Если канал не отвечает, команда сама выполняет возврат по журналу (5.7) и завершает оставшееся ядро. Только после этого удаляются задача и каталог в `%ProgramFiles%`. Каталог данных удаляется по флагу; при этом команда сообщает, что устройство `<имя ПК>-splitlane` остаётся в сети Tailscale и удаляется в её консоли.

Повторный `install` поверх существующей установки (новая сборка) сначала останавливает прежний служебный процесс: отправляет ему `helper.shutdown`, ждёт завершения и только потом заменяет файлы и задачу. Если канал не отвечает, команда сама выполняет возврат по журналу (5.7) и завершает оставшееся ядро, как `uninstall`.

Для разработки служебный процесс запускается вручную из повышенного терминала с флагом `--dev` и путями внутри репозитория.

## 5. Служебный процесс

### 5.1. Канал связи

- Именованный канал `\\.\pipe\SplitLane.Helper`. Описатель безопасности задаётся явно: доступ на чтение и запись имеют SYSTEM, администраторы и пользователь, чей SID записан при настройке.
- Сообщения — JSON, по одному в строке. Запрос: `{"id", "method", "params"}`. Ответ: `{"id", "result"}` или `{"id", "error": {"code", "message"}}`. У отдельных ошибок есть дополнительные поля: `protocol` у `protocol_mismatch`, `rules` у `rule_rejected` (8.3). События от служебного процесса: `{"event", "data"}`.
- Первое сообщение клиента — `hello` с номером версии протокола. При несовпадении служебный процесс отвечает ошибкой `protocol_mismatch`, в которой дополнительно передаёт номер своей версии (поле `protocol`), и после этого принимает только `helper.shutdown`. Если служебный процесс старше окна (обычный случай после новой сборки), окно показывает экран «Настройка» с кнопкой «Обновить служебный процесс»: это та же команда `install` (4.3). Если служебный процесс новее окна, окно показывает «Обновите приложение».

Методы:

| Метод | Параметры | Действие |
|---|---|---|
| `hello` | `protocol` | проверка версии; в ответе версии служебного процесса и ядра |
| `state.get` | — | полное состояние (5.2) |
| `routing.enable` | — | начать включение (5.3) |
| `routing.disable` | `skipRestore` (необязательно) | выключить (5.4); с `skipRestore: true` — выключить без возврата системного exit node |
| `routing.allDirect` | `on` | аварийный режим «всё напрямую» |
| `lanes.set` | `apps`, `defaultLane` | проверить, применить и сохранить раскладку (8.3) |
| `tailscale.login` | — | начать вход; ссылка приходит в состоянии |
| `tailscale.logout` | — | выйти из сети во встроенном узле |
| `tailscale.setExitNode` | `id` | выбрать exit node |
| `systemTailscale.clearExitNode` | — | выключить exit node в системном Tailscale (5.6) |
| `activity.subscribe` | `detailFor` (необязательно) | подписка на активность; с `detailFor` (ключ программы, 8.4) добавляются подробности одной программы |
| `diagnostics.export` | — | собрать журналы служебного процесса и ядра (рабочего и режима настройки) и снимок состояния в архив в `%ProgramData%\SplitLane\export\` (4.2), вернуть путь; конфиг ядра, каталог состояния встроенного узла и секреты в архив не попадают; если `state.json` не читается, архив отмечает это: снимок тогда — значения по умолчанию в памяти |
| `helper.shutdown` | — | выключить деление и завершить служебный процесс |

Других методов нет. Любой неизвестный метод — ошибка `unknown_method`.

События: `state` (полное состояние при каждом изменении), `activity` (раз в секунду, раздел 8.4).

Правила обмена:

- Версия протокола — целое число, на этапе 1 равна 1. Ответ `hello`: `{ "protocol": 1, "helper": "x.y.z", "core": "1.14.4" }`.
- `routing.enable`, `routing.disable`, `routing.allDirect`, методы `tailscale.*`, `systemTailscale.clearExitNode` и `helper.shutdown` отвечают сразу после проверки параметров и фазы; ход и итог окно видит в событиях `state`. `lanes.set` и `diagnostics.export` отвечают по завершении.
- Команды, меняющие состояние, обрабатываются по одной, в порядке поступления, от какого бы клиента они ни пришли. Пока идёт применение раскладки или режима «всё напрямую» (сверка до 3 секунд, 8.3), следующая команда ждёт. Переходы `starting` и `stopping` очередь не занимают: в них действует таблица ниже.
- `error.code` — строка из закрытого списка: `bad_request`, `unknown_method`, `protocol_mismatch`, `wrong_phase`, `busy`, `rule_rejected`, `apply_failed`, `unknown_exit_node`, `internal`. `error.message` — текст для журнала; окно показывает текст из словаря по коду (9.7).
- Повторный `activity.subscribe` заменяет подписку; подписка действует до закрытия соединения. Канал принимает несколько клиентов одновременно (второй клиент — сценарная проверка); события получают все.

Поведение методов по фазам (сочетание, которого нет в таблице, — ошибка `wrong_phase`):

| Метод | `off`, `error` | `starting` | `on`, `degraded`, `blocked` | `stopping` |
|---|---|---|---|---|
| `routing.enable` | начать включение | без действия | в `degraded` — внеочередная проверка связи (действие «Повторить»); иначе без действия | `busy` |
| `routing.disable` | перейти в `off` | прервать включение, откат 5.4 | выключение 5.4 | при причине `restore_pending` — внеочередная попытка возврата (действие «Повторить»); без неё — без действия, а если за этим выключением должно последовать включение (смена exit node, старт 5.7 с признаком «было включено», перезапуск ядра 5.5), оно отменяется: итоговая фаза `off` (или `error` с `adapter_left`, 5.4); с `skipRestore: true` — выключение без возврата (5.4) |
| `routing.allDirect` | `wrong_phase` | `busy` | в `on` и `degraded` — применить; в `blocked` — `wrong_phase` | `busy` |
| `lanes.set` | проверить и сохранить | `busy` | проверить, применить, сохранить (8.3) | `busy` |
| `tailscale.setExitNode` | сохранить | `busy` | сохранить, затем выключение и повторное включение | `busy` |
| `tailscale.login` | режим настройки и вход | `busy` | в `degraded` с `backend = expired` — выключение 5.4, затем режим настройки и вход; иначе `wrong_phase` | `busy` |
| `tailscale.logout` | выйти (раздел 7) | `busy` | `wrong_phase` | `busy` |
| `systemTailscale.clearExitNode` | `wrong_phase` | `busy` | в `blocked` — выполнить; иначе без действия | `busy` |
| `helper.shutdown` | завершиться | откат 5.4, завершиться | выключение 5.4, завершиться | дождаться конца выключения, завершиться |

`hello`, `state.get`, `activity.subscribe` и `diagnostics.export` работают в любой фазе.

### 5.2. Состояние

```json
{
  "phase": "off | starting | on | degraded | blocked | stopping | error",
  "reason": { "code": "…", "params": {} },
  "allDirect": false,
  "defaultLane": "vpn | direct",
  "apps": [ "…правила, раздел 8.1…" ],
  "addresses": { "vpn": "адрес или null", "direct": "адрес или null" },
  "tailscale": {
    "backend": "stopped | needs_login | starting | running | needs_approval | expired",
    "authUrl": "ссылка для входа или null",
    "deviceName": "имя встроенного узла",
    "exitNodes": [ { "id": "", "name": "", "online": true } ],
    "selectedExitNode": "id или null",
    "path": "direct | relay | null"
  },
  "systemTailscale": { "installed": true, "exitNodeOn": false, "restoreOnDisable": true }
}
```

Пояснения к полям:

- `reason` равен `null`, если причины нет.
- `tailscale.backend`: `stopped` — ядро не запущено; `needs_approval` — ссылка для входа использована, узел ждёт одобрения администратором сети Tailscale; признак «вход выполнен» (раздел 7) в этом состоянии не ставится. Пока ядро не запущено, `exitNodes` и имя выбранного exit node берутся из последнего сохранённого списка.
- `tailscale.path` — вид соединения встроенного узла с выбранным exit node: прямое (`direct`) или через ретранслятор (`relay`); `null`, когда вид неизвестен (раздел 7).
- `systemTailscale.installed` и `exitNodeOn` обновляются по правилам 5.6. `restoreOnDisable` равен `true`, пока существует журнал возврата (5.7).

Фазы:

- `off` — виртуального адаптера нет, система в исходном состоянии (ядро не запущено или работает в режиме настройки, раздел 7).
- `starting` — идёт включение или перезапуск ядра (5.5).
- `on` — обе дорожки работают.
- `degraded` — ядро работает, но дорожка VPN недоступна (сервер не отвечает, истёк вход).
- `blocked` — в системном Tailscale снова включён exit node, его блокировка мешает делению.
- `stopping` — идёт выключение, возврат системного exit node по журналу или остановка ядра, оставшегося от прошлого запуска (5.7).
- `error` — включение не удалось или работа прервана сбоем; система возвращена в исходное состояние (кроме причины `adapter_left`: адаптер ядра остался), в `reason` причина.

Признак `allDirect` не сохраняется в `state.json` и сбрасывается при выключении, перезапуске ядра и перезапуске служебного процесса: после них действует обычный режим.

Коды причины: `no_default_route`, `ip_forwarding`, `other_core`, `not_logged_in`, `no_exit_node`, `system_dns_override`, `config_invalid`, `core_start_timeout`, `tunnel_not_proven`, `same_address`, `switch_check_failed`, `leak_detected`, `core_crashed`, `core_unresponsive`, `vpn_unreachable`, `login_expired`, `restore_pending`, `adapter_left`. Текст для экрана окно берёт из словаря по коду (9.7). Для `restore_pending` в `params` передаются команда для ручного восстановления и текст ошибки последней попытки.

Переходы: `off`, `error` → `starting` по `routing.enable`; `starting` → `on` (шаг 9) либо → `stopping` → `error` (сбой); `on` ↔ `degraded` (5.5); `on`, `degraded` → `blocked`, когда в системном клиенте выбран exit node, и обратно, когда он снят (если выполняются оба условия, фаза `blocked`); `on`, `degraded`, `blocked` → `stopping` → `off` по `routing.disable`; перезапуск ядра по 5.5 идёт в фазе `starting`; `error` → `off` по `routing.disable` и при перезапуске служебного процесса; `starting` → `stopping` → `off` по `routing.disable` (отмена включения); `on`, `degraded` → `stopping` → `error`, если трафик идёт в обход VPN (5.5); `stopping` → `error` с причиной `adapter_left` (5.4). Те же переходы в `off` выполняются по `helper.shutdown` и по `tailscale.login` при истёкшем входе; по `tailscale.setExitNode` за выключением сразу следует включение. При старте служебного процесса с журналом возврата или с оставшимся ядром начальная фаза — `stopping`, затем `off` либо, если установлен признак «было включено», сразу `starting` (5.7). Без журнала и без оставшегося ядра начальная фаза — `off` либо, по тому же признаку, `starting`.

Раскладка, основная дорожка, выбранный exit node, признак «вход выполнен», последний список exit node (раздел 7), признак «было включено», идентификатор процесса ядра и время его создания (5.7) хранятся в `%ProgramData%\SplitLane\state.json`. Источник истины — служебный процесс. Признак «было включено» ставится при переходе в фазу `on`. Он снимается при любом переходе в фазу `off` или `error` (в том числе по `routing.disable`, `helper.shutdown` и `tailscale.login` при истёкшем входе) и при завершении сеанса Windows. Когда одна из этих трёх команд начинает выключение 5.4, признак снимается сразу, в его начале. Перезапуск ядра по 5.5 идёт в фазе `starting` и признак не снимает. Если служебный процесс при старте находит признак установленным, прошлый экземпляр завершился аварийно: после возврата по журналу (5.7) деление включается заново. Настройка «Включать деление при запуске» хранится у окна: окно само отправляет `routing.enable` после подключения. Сведения для возврата системного exit node хранятся отдельно, в журнале возврата (5.7).

### 5.3. Включение

Порядок проверен на практике (приложение A) и не меняется местами.

1. **Предварительные проверки.** Отказ с понятной причиной, если: встроенный узел не вошёл в сеть (по сохранённому признаку «вход выполнен», раздел 7); exit node не выбран; у компьютера нет маршрута по умолчанию; на физическом адаптере включена пересылка IPv4 (общий доступ к интернету, мобильная точка доступа); уже запущено другое ядро sing-box (собственное ядро в режиме настройки не считается: оно останавливается перед шагом 3); системный Tailscale управляет DNS и действует его правило для всех имён (правило NRPT «.»): запросы имён шли бы мимо адаптера ядра и блокировались бы (причина `system_dns_override`). При включении без участия пользователя (повторное включение после сбоя, включение при старте служебного процесса) отсутствие маршрута по умолчанию — не отказ: служебный процесс ждёт сеть до 60 секунд.
2. Прочитать, выбран ли exit node в системном Tailscale (`tailscale status --json`, поле `ExitNodeStatus`) и с каким признаком доступа к локальной сети (`tailscale debug prefs`, поле `ExitNodeAllowLANAccess`; в `status --json` этого признака нет).
3. Записать оба файла правил из сохранённой раскладки (6.5), собрать конфиг ядра (раздел 6) с начальным режимом (6.3), проверить его командой `sing-box check`.
4. Запустить ядро, дождаться строки запуска, записанной именно этим процессом ядра, а не оставшейся в журнале от прошлого запуска (не дольше 30 секунд). Если узел после запуска сообщает, что нужен вход, — откат сразу, без ожидания шага 5, с причиной `login_expired`; признак «вход выполнен» снимается. Перед запуском служебный процесс удаляет неподключённое устройство Wintun с именем своего адаптера, если оно осталось после принудительного завершения ядра (приложение A, проверки плана 1B).
5. **Доказать, что туннель работает, не трогая системный VPN:** запрос через локальный вход `probe-vpn` должен пройти, а внешний адрес должен отличаться от адреса через `probe-direct` (не дольше 45 секунд). Если запрос через `probe-vpn` или через `probe-direct` не прошёл — откат с причиной `tunnel_not_proven`: без адреса прямой дорожки сравнивать не с чем. Если адреса совпали — откат с причиной `same_address`. Если доказать не удалось (`tunnel_not_proven`), служебный процесс один раз останавливает это ядро и повторяет шаги 3–5 с новыми портами: собственный DNS ядра иногда первые десятки секунд не получает ответов (приложение A, проверки плана 1B); откат — только после второй неудачи.
6. Если в системном Tailscale был выбран exit node — записать журнал возврата (5.7), если его ещё нет, и только после этого выключить exit node командой `tailscale set --exit-node=`.
7. Сбросить кэш DNS Windows.
8. Проверить путь через адаптер: служебный процесс разрешает имя и делает запрос обычным способом; его собственный трафик встроенным правилом закреплён за дорожкой VPN, внешний адрес не должен совпадать с адресом прямой дорожки из шага 5 (совпадения с адресом VPN из шага 5 не требуется: внешний адрес exit node может меняться). Два успешных прохода подряд, не дольше 45 секунд.
9. Фаза `on`.

Сбой на любом шаге — откат по правилам 5.4 и фаза `error`. Признак ухода напрямую — ответ с адреса прямой дорожки два раза подряд; тогда откат выполняется немедленно, без ожидания остального времени. Один такой ответ утечкой не считается: ядро изредка не определяет программу-владельца соединения, и запрос служебного процесса уходит по основной дорожке.

### 5.4. Выключение и откат

1. Если есть журнал возврата (5.7) — включить exit node обратно значением из журнала (команда `tailscale set --exit-node=<адрес> --exit-node-allow-lan-access=<признак>`) и **дождаться подтверждения** по `tailscale status --json` (в `ExitNodeStatus` тот же адрес); после подтверждения журнал удаляется. Пока подтверждения нет, ядро не останавливается и служебный процесс не завершается; попытки повторяются каждые 5 секунд. Если возврат не подтверждён за 30 секунд, фаза `stopping` получает причину `restore_pending`; окно показывает текст ошибки команды, команду для ручного восстановления и действия «Повторить» и «Выключить без возврата». Второе — явное решение пользователя (`routing.disable` с параметром `skipRestore: true`): журнал возврата удаляется, ядро останавливается, фаза `off`. Без такого решения ядро не останавливается.
2. Остановить ядро: штатный сигнал, ожидание не дольше 5 секунд, затем принудительное завершение. Штатный сигнал — `CTRL_BREAK_EVENT` группе процессов ядра (ядро запускается в отдельной группе процессов); способ проверяется на ПК до основного кода (раздел 12). Если сигнал отправить не удалось, принудительное завершение выполняется сразу.
3. Убедиться, что адаптер ядра исчез. Итоговая фаза: `off` при выключении и при отмене включения; `error` при откате после сбоя (неудачное включение, 5.3; трафик в обход VPN, 5.5); при перезапуске ядра (5.5, раздел 10) фаза остаётся `starting`; при старте служебного процесса — по 5.7. Если адаптер не исчез за 10 секунд — фаза `error` с причиной `adapter_left`.

То же выполняется при `helper.shutdown` и при выходе из приложения через трей. При завершении сеанса Windows (выход из системы, перезагрузка, выключение) порядок сокращён, потому что система даёт процессу около 5 секунд и затем завершает его: служебный процесс снимает признак «было включено», один раз отдаёт команду возврата системного exit node и завершает ядро, не дожидаясь подтверждения. Ядро получает то же уведомление и может завершиться раньше; порядка это не меняет. Если подтверждение не успело прийти, журнал возврата остаётся и отрабатывается при следующем старте (5.7). Правило «не останавливать ядро без подтверждения» на завершение сеанса не распространяется. Уведомление о завершении сеанса служебный процесс получает сам, без участия окна; способ (скрытое окно с сообщениями `WM_QUERYENDSESSION` и `WM_ENDSESSION`; консольное событие не приходит процессу, загрузившему `user32.dll`) проверяется на ПК до основного кода (раздел 12).

### 5.5. Надзор за ядром

- Отдельный поток ждёт завершения процесса ядра. При неожиданном завершении он сразу включает системный exit node (если есть журнал возврата, 5.7), не дожидаясь основного цикла.
- После этого служебный процесс перезапускает ядро по порядку 5.3, не более трёх раз с нарастающей паузой. При неудаче — фаза `error`.
- Раз в 10 секунд выполняются две проверки. Первая — дорожка VPN через `probe-vpn`. Три неудачи подряд при работающем `probe-direct` — фаза `degraded`. Если одновременно не отвечает и `probe-direct`, это отсутствие сети или отказ сервиса проверки, а не VPN: фаза не меняется, DNS не переключается. Вторая — путь через адаптер, как на шаге 8 включения (в фазе `blocked` не выполняется). Если два прохода подряд ответ приходит с адреса прямой дорожки, трафик идёт в обход VPN: откат 5.4, фаза `error`. Если запрос через адаптер не проходит три раза подряд при работающем `probe-vpn`, ядро считается неисправным и перезапускается: откат 5.4, затем включение 5.3. При `degraded` ядро не останавливается: программы дорожки VPN остаются без связи, а не уходят напрямую.
- Каждая проверка — запрос внешнего адреса с тайм-аутом 5 секунд. Неудача — тайм-аут или ошибка соединения; ответ сервиса с ошибкой HTTP неудачей связи не считается. Возврат из `degraded` в `on` — после одной удачной проверки `probe-vpn`. Поле `addresses` (5.2) обновляется при каждой удачной проверке.
- В фазе `degraded` разрешение имён переключается на DNS провайдера, чтобы программы прямой дорожки продолжали работать (раздел 6.3). При восстановлении дорожки VPN всё возвращается.
- При старте служебный процесс действует по журналу возврата (5.7), затем останавливает своё ядро, оставшееся от прошлого запуска, и только после этого включает деление заново, если установлен признак «было включено» (5.2).

### 5.6. Согласование с системным Tailscale

- Системный Tailscale не обязателен. Если он не установлен, шаги с ним пропускаются. Если клиент установлен, но его служба остановлена или вход в нём не выполнен, считается, что exit node не выбран.
- `tailscale.exe` вызывается по полному пути из каталога установки клиента, без поиска по `PATH`.
- Пока деление включено, служебный процесс раз в 3 секунды читает `tailscale status --json`. Если пользователь снова выбрал exit node в системном клиенте — фаза `blocked`: блокировка Tailscale не пропускает трафик программ в адаптер ядра. Окно предлагает два действия: выключить exit node в системном клиенте (`systemTailscale.clearExitNode`) или выключить деление.
- Пока деление выключено, а окно подключено, `systemTailscale.installed` и `exitNodeOn` обновляются с тем же интервалом: они нужны для предупреждения перед включением (9.5).
- Процессы системного Tailscale (`tailscaled.exe`, `tailscale-ipn.exe`) всегда идут напрямую встроенным правилом; закрепить их за дорожкой VPN нельзя.

### 5.7. Журнал возврата системного exit node

Выключенный на шаге 6 exit node — сохранённая настройка системного Tailscale, она переживает перезагрузку. Чтобы вернуть её после любого сбоя, служебный процесс ведёт журнал `%ProgramData%\SplitLane\restore.json`.

- Журнал записывается перед шагом 6 включения: адрес exit node системного Tailscale и признак доступа к локальной сети. Запись атомарная и сброшена на диск до вызова `tailscale set`. Идентификатор процесса ядра и время его создания служебный процесс записывает в `state.json` после каждого запуска ядра (5.3, шаг 4; режим настройки, раздел 7), независимо от журнала.
- Журнал удаляется только после подтверждённого возврата (5.4, шаг 1) или по явному решению пользователя «Выключить без возврата» (5.4).
- Пока журнал существует, включение его не перезаписывает: при перезапусках ядра (5.5) возвращается значение, прочитанное до первого выключения.
- Если к моменту возврата в системном Tailscale уже выбран exit node (его выбрал сам пользователь, фаза `blocked`), выбор пользователя не меняется, а журнал удаляется. По `systemTailscale.clearExitNode` в журнал записывается exit node, выбранный пользователем в этот момент.
- Пока журнал существует, а ядро не работает, служебный процесс повторяет возврат каждые 5 секунд до подтверждения, в том числе после срабатывания потока надзора (5.5).
- При старте служебный процесс первым делом читает журнал. Если журнал есть, фаза — `stopping`: выполняется шаг 1 из 5.4, независимо от того, осталось ли ядро от прошлого запуска, затем оставшееся ядро останавливается. Если журнала нет, а ядро осталось, оно останавливается в той же фазе `stopping` (5.4, шаги 2 и 3). Своё ядро служебный процесс опознаёт по идентификатору процесса и времени создания из `state.json` и по пути образа в `%ProgramFiles%\SplitLane\`; чужой процесс `sing-box.exe` он не трогает. Канал в это время уже работает, окно видит фазу и причину.

## 6. Конфигурация ядра

Версия ядра зафиксирована: sing-box 1.14.4. Конфиг генерируется только под неё. Переход на другую версию — отдельная задача с повторной сценарной проверкой.

### 6.1. Общая схема

- **Входы:** виртуальный адаптер `SplitLane` (адреса IPv4 и IPv6, `auto_route`, `strict_route`, стек `gvisor`, исключены диапазоны сети Tailscale `100.64.0.0/10` и `fd7a:115c:a1e0::/48`); два локальных прокси-входа на `127.0.0.1` со случайными портами: `probe-vpn` и `probe-direct`.
- **Выходы:** встроенный узел Tailscale `vpn` (каталог состояния в `%ProgramData%`, имя устройства `<имя ПК>-splitlane`, выбранный exit node, без системного интерфейса); прямой выход `direct`.
- **Без разбора протоколов.** Правила `sniff` в конфиге нет. Проверка показала, что с ним по дорожке VPN теряются UDP-пакеты больше примерно 1250 байт, а без него проходят.
- `route.auto_detect_interface` и `route.find_process` включены: первое привязывает собственные соединения ядра к физическому адаптеру, второе нужно, чтобы правила по процессам из перечитываемых файлов срабатывали.
- Локальный API ядра (`clash_api`) и служба API (`api`) слушают `127.0.0.1`, каждый на своём случайном порту со своим случайным секретом. Порты и секреты создаются при каждом запуске и известны только служебному процессу; если порт занят, запуск повторяется с новыми. Служба API входит и в конфиг режима настройки (раздел 7).
- Журнал ядра пишется в файл в `%ProgramData%\SplitLane\` на уровне `info`, без цветовых кодов: строка запуска (5.3, шаг 4) и ссылка для входа пишутся на этом уровне. В режиме разработки флаг `--core-log-level debug` включает подробный журнал для разбора сбоев. У ядра режима настройки (раздел 7) свой журнал, `logs\core-setup.log`: его запуски не откладывают журнал рабочего ядра, нужный для разбора его сбоя. Архив диагностики (5.1) берёт оба журнала ядра вместе с журналами предыдущего запуска.

### 6.2. Порядок правил маршрутизации

0. Входящие соединения с узла Tailscale (вход `vpn`) → отклонить.
1. Весь IPv6 отклоняется (ответы DNS выдаются только IPv4).
2. Вход `probe-vpn` → `vpn`; вход `probe-direct` → `direct`.
3. Порт 53 → перехват DNS.
4. Собственные адреса адаптера → отклонить (защита от петли).
5. Процессы системного Tailscale → `direct`.
6. Служебный процесс SplitLane → `vpn`.
7. Частные и локальные адреса → `direct`.
8. Режим ядра `alldirect` («всё напрямую») → `direct`.
9. Файл правил прямой дорожки → `direct`.
10. Файл правил дорожки VPN → `vpn`.
11. Основная дорожка — по одному правилу на режим ядра (6.3): `direct` и `direct-localdns` → `direct`; `vpn` и `vpn-localdns` → `vpn`. Итоговое правило — `vpn`.

Встроенные правила 5 и 6 задаются полным путём процесса, регулярным выражением без учёта регистра, как в 6.5.

Правило 0 закрывает доступ из сети Tailscale к самому ПК. Встроенный узел передаёт ядру каждое соединение, которое другое устройство сети Tailscale открывает на адрес узла, с входом `vpn` и адресом назначения, заменённым на `127.0.0.1` (ядро 1.14.4, `protocol/tailscale/endpoint.go`). Без правила 0 такое соединение ушло бы по правилу 7 в `direct` и достало бы службы ПК, слушающие только `127.0.0.1`, в том числе локальный API ядра и службу API (раздел 11). Собственные соединения узла (сервер управления, ретрансляторы, обмен с другими узлами) через правила маршрутизации не проходят, пробы и адаптер — это другие входы, а к службе API и локальному API ядра служебный процесс подключается по `127.0.0.1` мимо правил, поэтому правило 0 ему не мешает. Правило 0 — единственное правило маршрутизации в конфиге режима настройки (раздел 7): там без правил итоговым выходом стал бы `direct`.

### 6.3. Переключатели без перезапуска

Три вещи меняются во время работы без перезапуска ядра: основная дорожка, режим «всё напрямую» и запасной DNS в фазе `degraded`. Все три реализуются через режим ядра (`clash_mode`), который служебный процесс переключает через локальный API (`PATCH /configs`). Режимов пять: `vpn`, `vpn-localdns`, `direct`, `direct-localdns` (основная дорожка в обычном виде и с запасным DNS) и `alldirect` (DNS всегда локальный, основная дорожка значения не имеет).

Конфиг учитывает четыре свойства ядра 1.14.4:

- В одном правиле указывается один режим, поэтому правило 11 из 6.2 и правила DNS пишутся по одному на режим.
- Ядро знает только режимы, упомянутые в правилах маршрутизации и DNS, и режим по умолчанию. Переход на неизвестный режим оно молча игнорирует, а API отвечает успехом. Поэтому каждый из пяти режимов упомянут в правиле маршрутизации (для `vpn` и `vpn-localdns` это явное правило → `vpn`, повторяющее итоговое), а после каждого переключения служебный процесс читает `GET /configs` и считает его выполненным только при совпадении поля `mode`.
- Режим не сохраняется между запусками ядра (`cache_file` не включается). `clash_api.default_mode` в конфиге равен режиму, нужному на момент запуска, в том числе при перезапуске по 5.5.
- Смена режима не закрывает открытые соединения. После неё служебный процесс приводит соединения в соответствие с дорожками (8.3). Запрос `DELETE /connections` без идентификатора не используется: он сбрасывает сеть ядра целиком.

Правила с `clash_mode` для маршрутов и для DNS и переключение из каждого стартового режима в каждый проверяются на настоящем ядре до основного кода (раздел 12). Если они не работают, запасной способ — отдельные файлы правил, перечитываемые на лету; интерфейс служебного процесса от этого не меняется.

### 6.4. DNS

- Пока дорожка VPN работает, все имена разрешаются через шифрованный DNS (`1.1.1.1`, DNS-over-HTTPS), запросы идут через дорожку VPN. Провайдер в это время не видит запросов и не может подменить ответы.
- Собственные запросы ядра (адреса серверов Tailscale) и запросы прямого выхода идут через DNS физического адаптера.
- В фазе `degraded` и в режиме «всё напрямую» все имена, включая запросы программ дорожки VPN, разрешаются через DNS физического адаптера: провайдер видит эти имена и может подменить ответы. Сами соединения программ дорожки VPN в фазе `degraded` напрямую не идут. При каждом переключении DNS, в обе стороны, служебный процесс сбрасывает кэш DNS Windows: ядро при смене режима очищает только собственный кэш.
- В конфиге включено обратное сопоставление ответов DNS (`dns.reverse_mapping`) — только ради имён узлов в списке соединений (8.4). По умолчанию оно выключено и на практике не проверялось; проверяется на ПК до основного кода (раздел 12).

Известное ограничение: имена для программ прямой дорожки разрешаются с точки зрения сервера VPN, поэтому сети раздачи контента могут выдавать им не самые близкие серверы. Раздельный DNS по дорожкам вынесен за этап 1.

### 6.5. Файлы правил дорожек

- Два файла в `%ProgramData%\SplitLane\rules\`: для дорожки VPN и для прямой. Формат — исходный формат наборов правил sing-box, версия 3. Ядро перечитывает их при изменении. Файлы записываются при включении (5.3, шаг 3) и при каждом `lanes.set`, пока ядро работает (8.3).
- В файлах только правила по пути процесса в виде регулярных выражений без учёта регистра (`process_path_regex`) и логические правила из них для исключений (8.2); в одном объекте правила одно поле.
- Файл никогда не бывает пустым: в нём всегда есть служебная запись-заглушка.
- Запись атомарная: временный файл в том же каталоге, затем переименование; кодировка UTF-8 без метки порядка байтов. Если переименование получило отказ (ядро в этот момент читает файл), оно повторяется. Имя файла, включая регистр букв, совпадает с путём в конфиге. Каталог `rules\` не удаляется и не пересоздаётся, пока ядро работает: иначе ядро перестаёт следить за файлами до перезапуска.
- Перед записью каждое выражение компилируется в служебном процессе. Go и ядро используют один и тот же синтаксис регулярных выражений, поэтому ошибка ловится до записи.
- Об успешном перечитывании ядро не сообщает; при ошибке оно пишет в журнал строку `reload rule-set`. Как служебный процесс подтверждает применение и что делает при ошибке, описано в 8.3.

## 7. Коннектор Tailscale

- **Вход и режим настройки.** По `tailscale.login` служебный процесс запускает ядро в режиме настройки. Конфиг режима настройки: встроенный узел, локальный сервер DNS, `route.default_domain_resolver`, служба API и единственное правило маршрутизации — отклонить входящие соединения с узла (правило 0 из 6.2); DNS отвечает только адресами IPv4 (`dns.strategy: ipv4_only`, как в рабочем конфиге: потерянный ответ на запрос A иначе оставлял узлу только адреса IPv6, а IPv6, ведущий в никуда — exit node системного Tailscale без IPv6, — держал его минутами без ссылки для входа; приложение A, проверки плана 1B); виртуального адаптера нет, `route.auto_detect_interface` не задаётся. Причина: без адаптера со `strict_route` блокировка системного Tailscale (включённый exit node) не выпускает ядро через физический адаптер, и связь с сервером управления Tailscale возможна только обычным маршрутом системы — так вход прошёл в проверке. Канал данных встроенного узла в этом режиме при включённом системном exit node не работает; это ожидаемо, проверки связи в режиме настройки не выполняются. Система при этом не меняется. Ссылка для входа попадает в состояние, окно открывает её в браузере. После входа состояние узла сохраняется в `%ProgramData%\SplitLane\tailscale\` и переживает перезапуски.

  Режим настройки и рабочее ядро никогда не работают одновременно: у них общий каталог состояния узла. Режим настройки работает только в фазах `off` и `error`, фаза при этом не меняется. Он запускается по `tailscale.login`, а также при подключении окна, если вход уже был выполнен (чтобы показать состояние узла и список exit node). Он останавливается первым действием включения, до шага 3 (служебный процесс дожидается завершения процесса), через 5 минут после отключения последнего окна и при `helper.shutdown`.

  Вход считается выполненным, когда ссылки для входа нет и узел получил адрес в сети Tailscale (`backend` равен `starting` или `running`). Ждать `running` нельзя: при включённом системном exit node узел в режиме настройки остаётся в `starting`. Признак «вход выполнен» и последний полученный список exit node сохраняются в `state.json`; на них опирается предварительная проверка 5.3, когда ядро не запущено. Окончательно вход подтверждает шаг 5 включения.

  `tailscale.logout` выполняется только при выключенном делении: служебный процесс запускает режим настройки, если он не запущен, выполняет выход через ядро и стирает признак «вход выполнен».
- **Источник данных о узле.** Окну нужны: ссылка для входа, состояние узла, список exit node. Основной источник — служба API ядра версии 1.14; из неё же берётся вид соединения с выбранным exit node (`tailscale.path`, 5.2). Запасной способ, если служба API не подходит: ссылка для входа и состояние узла — из строк журнала ядра; список exit node — из `tailscale status --json` системного клиента; если системного клиента нет, шаг 2 экрана «Подключите VPN» показывает поле для адреса exit node в сети Tailscale; `tailscale.logout` останавливает ядро и удаляет каталог состояния узла; `tailscale.path` равен `null`, плашка в шапке показывает только «Tailscale · имя». Служба API (тип `api`, адрес `127.0.0.1`, секрет) проверяется на настоящем ядре до основного кода (раздел 12) и принимается основным источником, если в обычном режиме и в режиме настройки она отдаёт ссылку для входа, состояние узла и список узлов с признаками «может быть exit node» и «в сети». Интерфейс служебного процесса от выбора не зависит. Соединения, счётчики, закрытие соединений и режим ядра в обоих случаях идут через Clash API, проверенный на практике (приложение A).
- **Выбор exit node** сохраняется в состоянии. Смена exit node при включённом делении выполняется как выключение и повторное включение. `exitNodes[].id` — адрес IPv4 узла в сети Tailscale; он же записывается в поле `exit_node` конфига (поле принимает имя или адрес узла, но не внутренний идентификатор, которым пользуется служба API). `name` — имя узла.
- **Истечение входа.** Если узел сообщает, что нужен повторный вход, фаза становится `degraded`, `tailscale.backend` — `expired`, окно показывает действие «Выключить деление и войти». По `tailscale.login` в этом состоянии служебный процесс сначала выполняет выключение 5.4 и только потом запускает режим настройки: в фазе `degraded` браузер из дорожки VPN без связи и страницу входа не откроет. После входа пользователь включает деление сам. Как ядро выдаёт новую ссылку после истечения срока, проверяется на ПК до основного кода (раздел 12).
- **Имя устройства** — `<имя ПК>-splitlane`, чтобы его было легко отличить в консоли Tailscale.

## 8. Программы и дорожки

### 8.1. Правило программы

```json
{
  "id": "устойчивый идентификатор",
  "name": "отображаемое имя",
  "exe": "путь к файлу, с которого программу добавили",
  "matcher": { "kind": "folder | file | package | system", "value": "…" },
  "lane": "vpn | direct"
}
```

Хранятся только закреплённые программы. Незакреплённые в состоянии не хранятся и появляются из живой активности.

`id` — UUID, его создаёт окно. `matcher.value` вычисляет только служебный процесс: правило «папка программы» из 8.2 реализовано один раз, в нём, и им же группируется активность (8.4). Для нового правила окно передаёт `exe`, `matcher.kind` и пустой `value`; служебный процесс заполняет `value` и возвращает правило в `state.apps`. Существующие правила окно передаёт без изменений. Смена вида в карточке («Вся папка программы») — это `lanes.set` с тем же `id`, другим `kind` и пустым `value`.

Формат `value`: `folder` — абсолютный путь папки с завершающей обратной чертой; `file` — абсолютный путь файла; `package` — `<имя пакета>_<идентификатор издателя>/<имя файла>`, оба берутся из пути внутри `WindowsApps`; `system` — пустая строка. Регулярные выражения для 6.5 строит служебный процесс из `value`, с экранированием и без учёта регистра: `folder` — совпадение с началом пути, `file` — с путём целиком, `package` — папка пакета любой версии и имя файла, `system` — `svchost.exe` в системной папке и псевдопуть `:System`.

`name`: окно передаёт имя ярлыка, если программа добавлена из ярлыка или из списка установленных; иначе оставляет пустым, и служебный процесс подставляет описание файла из его ресурсов, а если его нет — имя файла без расширения.

### 8.2. Что считается программой

- `folder` — все исполняемые файлы в папке программы и вложенных папках. Это вид по умолчанию: обновлялки и вспомогательные процессы идут той же дорожкой. Папка программы — папка исполняемого файла; если её имя — номер версии (необязательная приставка `app-` и от двух до четырёх чисел через точку: `app-1.0.9`, `124.0.6367.91`), берётся папка уровнем выше.
- `file` — один исполняемый файл по точному пути. Используется, если пользователь выключил «Вся папка программы» в карточке, и когда папка программы общая: корень диска, `C:\Windows` и всё внутри неё, корень `C:\Program Files` или `C:\Program Files (x86)`, «Рабочий стол», «Загрузки», «Документы», временная папка пользователя. В этих случаях служебный процесс сам заменяет вид `folder` на `file`.
- `package` — приложение из Магазина Windows: имя пакета и имя файла, без версии в пути, потому что путь меняется при каждом обновлении.
- `system` — плитка «Службы Windows»: `svchost.exe` и трафик ядра системы. Перемещается как одно целое.

Служебный процесс отклоняет правило, если оно: охватывает корень диска, `C:\Windows`, `C:\Program Files` или `C:\Program Files (x86)` целиком; совпадает со служебным процессом SplitLane, ядром или процессами системного Tailscale.

Если правила разных дорожек вложены одно в другое (папка одного правила содержит папку или файл другого), действует более узкое правило: `file` и `package` важнее `folder`, вложенная папка важнее внешней. Порядок файлов (6.2, правила 9–10) этого не обеспечивает: при раскладке «папка Steam — напрямую, игра внутри неё — через VPN» игра подошла бы под оба файла и ушла бы напрямую. Поэтому служебный процесс при записи файлов добавляет к более широкому правилу исключения: оно записывается как логическое правило «путь подходит под это правило И НЕ подходит под вложенные правила другой дорожки» (`type: logical`, `mode: and`, вложенное правило с `invert: true`). Два правила с одинаковым охватом в разных дорожках служебный процесс отклоняет. Группировка активности (8.4) и сверка соединений (8.3) определяют дорожку программы по тому же порядку. Если проверка на ПК (раздел 12) покажет, что логическое правило с `invert` в перечитываемом файле не работает, правила 9 и 10 в 6.2 меняются местами (при пересечении побеждает дорожка VPN), а раскладку, в которой правило прямой дорожки вложено в более широкое правило дорожки VPN, служебный процесс отклоняет.

### 8.3. Применение раскладки

По `lanes.set` служебный процесс:

1. Проверяет всю раскладку (8.2). `lanes.set` заменяет раскладку целиком и неделим: если отклонено хотя бы одно правило, ничего не сохраняется и не применяется, ответ — ошибка `rule_rejected`; список отклонённых правил передаётся в её поле `rules`: `[ { "id", "reason" } ]`. `reason` — код причины по 8.2: `too_broad` (охват шире разрешённого), `protected` (служебный процесс SplitLane, ядро, системный Tailscale), `duplicate` (тот же охват в другой дорожке), `nested` (только в запасном варианте 8.2: правило прямой дорожки внутри правила дорожки VPN). Текст для экрана окно берёт из словаря по коду (9.7).
2. Если ядро работает (фазы `on`, `degraded`, `blocked`): записывает файлы правил (6.5) и переключает режим ядра (6.3). Ядро перечитывает файл примерно за секунду и сообщает только об ошибке, строки об успехе у него нет. Поэтому следующие 3 секунды служебный процесс каждые 250 мс сверяет список соединений ядра с новой раскладкой и закрывает через API каждое соединение, которое идёт не по своей дорожке. Сверяются только соединения, чью дорожку определяют правила 8–11 из 6.2. Если в журнале ядра появилась строка об ошибке перечитывания или в конце срока остались расхождения, возвращаются прежние файлы правил и прежний режим, ответ — ошибка `apply_failed`.
3. Сохраняет раскладку в `state.json`, рассылает событие `state` и отвечает окну.

Та же сверка выполняется после включения и выключения режима «всё напрямую»: иначе соединения программ дорожки VPN, открытые напрямую, продолжали бы идти напрямую после возврата обычного режима. Если режим ядра не переключился (6.3) или в конце срока остались расхождения, возвращается прежний режим, признак `allDirect` в состоянии не меняется; служебный процесс и в этом случае рассылает событие `state`, из него окно узнаёт итог.

Перенос работающей программы заметен как короткий разрыв её соединений.

### 8.4. Живая активность

Служебный процесс получает от ядра список соединений с путём процесса, дорожкой и счётчиками и раз в секунду отправляет окну сводку:

```json
{
  "lanes": { "vpn": { "down": 0, "up": 0 }, "direct": { "down": 0, "up": 0 } },
  "apps": [
    { "key": "", "kind": "app | system | unattributed", "name": "", "exe": "", "ruleId": "id или null", "lane": "vpn", "down": 0, "up": 0, "connections": 0 }
  ],
  "detail": { "key": "", "exes": [ "…" ], "connections": [ { "host": "имя или адрес", "lane": "vpn", "down": 0, "up": 0 } ] }
}
```

- `down` и `up` — байты в секунду за последнюю секунду. Первый замер после включения, перезапуска ядра или перерыва в подписке только запоминает счётчики: по нему скорость ещё не посчитать, и сводка за эту секунду не отправляется.
- Соединения группируются по программе: для закреплённых — по правилу, для остальных — по папке программы (8.2).
- `key` — ключ группы: идентификатор правила для закреплённых программ, путь папки программы для незакреплённых, постоянные значения `system` и `unattributed` для незакреплённых особых плиток. Этот же ключ передаётся в `detailFor`.
- `exe` — исполняемый файл группы с наибольшим трафиком, по нему окно берёт значок. `name` — имя из правила, а для незакреплённых программ — описание этого файла из его ресурсов или имя файла без расширения.
- Соединения без процесса-владельца (WSL, виртуальные машины, часть системного трафика, а также соединения программ этого компьютера, для которых ядро не смогло определить процесс) собираются в плитку «WSL и виртуальные машины» (`kind: unattributed`). На этапе 1 она всегда идёт по основной дорожке и не перемещается.
- Незакреплённая программа остаётся в сводке, пока у неё есть соединения, и ещё 5 минут после последнего, с нулевыми скоростями. Особые плитки есть в каждой сводке; плитки `system` нет, пока службы Windows закреплены правилом вида `system`: их трафик показывает плитка этого правила.
- `detail` есть только при подписке с `detailFor`: перечень замеченных исполняемых файлов программы (для карточки, 9.4) и её соединения — адрес или имя узла, дорожка, скорость; не больше 500 соединений с наибольшим трафиком, чтобы сообщение уместилось в строку канала (5.1); число всех соединений программы — в её записи `connections`.
- Имена узлов в соединениях берутся из обратного сопоставления ответов DNS в ядре (6.4); если имени нет, показывается адрес.
- Событие `activity` отправляется, пока работает ядро с адаптером (фазы `on`, `degraded`, `blocked`). В остальных фазах незакреплённых программ нет: раздел «остальные программы» и вкладка «Сейчас в сети» пусты.

### 9.4. Карточка программы

Имя, значок, состояние («закреплена · через VPN»), кнопки смены дорожки и открепления. Блок «Что считается этой программой»: переключатель «Вся папка программы» и путь с перечнем замеченных исполняемых файлов. Блок «Соединения сейчас»: узел, дорожка, скорость. Вид соединения (например, «голос») на этапе 1 не показывается: ядро работает без разбора протоколов.

### 9.5. Первый запуск и состояния

- Экран «Настройка» — пока служебный процесс не установлен (4.3).
- Экран «Подключите VPN» — плитки способов подключения: Tailscale доступен, «Ключ или подписка» и «Файл настроек» показаны как будущие. Для Tailscale три шага: войти, выбрать exit node, включить. Перед включением показано предупреждение, что exit node в приложении Tailscale будет выключен на время работы и возвращён при выключении.
- После первого подключения тот же экран под названием «Подключение» открывается по нажатию на плашку подключения в шапке. На нём: имя устройства в сети Tailscale, выбранный exit node с возможностью смены (`tailscale.setExitNode`), действие «Выйти из Tailscale» (`tailscale.logout`, доступно при выключенном делении) и две настройки из 9.6. Отдельного экрана настроек на этапе 1 нет.
- Плашки состояний над дорожками:

| Фаза | Заголовок | Действия |
|---|---|---|
| `off` | Выключено. Программы ходят как обычно, без деления | Включить |
| `starting` | Включается… | Отменить |
| `degraded`, сервер недоступен | Сервер … недоступен. Программы дорожки VPN сейчас без связи. Имена сайтов временно разрешаются через DNS провайдера | Повторить, Всё напрямую |
| `degraded`, истёк вход | Нужно снова войти в Tailscale. На время входа деление будет выключено | Выключить деление и войти |
| `blocked` | В приложении Tailscale включён exit node. Он мешает делению | Выключить его, Выключить деление |
| `stopping` | Выключается… | — |
| `stopping`, возврат не подтверждён | Не удаётся вернуть exit node в приложении Tailscale | Повторить, Выключить без возврата |
| `error` | Не удалось включить: причина | Повторить, Сохранить журнал |

- В режиме «всё напрямую» плашка сообщает об этом и предлагает вернуть обычный режим.
- Если канал служебного процесса пропал, окно показывает плашку «Служебный процесс перезапускается», а если перезапуск не удался — «Служебный процесс не отвечает» с действием «Повторить» (раздел 10).

### 9.6. Трей и автозапуск

- Значок с четырьмя состояниями: работает, выключено, нужно действие, VPN без связи. Соответствие: «работает» — фаза `on`; «выключено» — `off`; «VPN без связи» — `degraded` с причиной `vpn_unreachable`; «нужно действие» — `blocked`, `error`, `degraded` с причиной `login_expired`, неподтверждённый возврат (`restore_pending`), режим «всё напрямую», не выполнена настройка. В фазах `starting` и `stopping` без причины значок не меняется.
- Меню: Открыть, Включить или Выключить, Выход. «Выход» выключает деление и завершает служебный процесс.
- Настройки: «Запускать при входе в Windows» (окно стартует свёрнутым в трей) и «Включать деление при запуске». Обе показаны на экране «Подключение» (9.5). Обе хранит окно в `%AppData%\SplitLane\`. При включённой второй окно после подключения к служебному процессу отправляет `routing.enable`, если фаза `off`; если включение завершилось причиной `no_default_route`, окно повторяет попытку каждые 10 секунд в течение 2 минут.
- Одновременно работает один экземпляр окна.

### 9.7. Оформление и тексты

- Тёмная тема: фон `#0e1014`, панели `#14171d`, карточки `#181c24`, границы `#232733`, текст `#e6e8ee`, приглушённый текст `#8b93a7`. Цвет дорожки VPN `#8b7cff`, прямой `#3ddc97`, предупреждение `#ffb454`, ошибка `#ff6b6b`. Цвета дорожек идут линией по верхнему краю дорожки и в заголовке.
- Шрифт интерфейса — системный (Segoe UI Variable); числа скорости — моноширинный (Cascadia Mono, Consolas) с табличными цифрами.
- Подписи дорожек: «Через VPN» и «Напрямую». В действиях: «Пустить через VPN», «Пустить напрямую». Одинаковые слова для одного и того же везде.
- Все строки интерфейса лежат в словаре по ключам. На этапе 1 словарь один, русский.

### 9.8. Технологии окна

Electron 45, React 19, TypeScript, electron-vite. Перетаскивание — `@dnd-kit/react`, версия зафиксирована точно. Состояние — небольшое хранилище (zustand). Стили — CSS-модули и переменные; готовые наборы компонентов не используются. Значки программ — `app.getFileIcon` с кэшем на диске; для плиток «Службы Windows» и «WSL и виртуальные машины» и для программ без значка — встроенные значки. Файлы из Проводника принимаются через `webUtils.getPathForFile`; ярлыки разрешаются в основном процессе через `shell.readShortcutLink`. Окно не обращается к сети, кроме канала служебного процесса.

## 10. Поведение при сбоях

| Событие | Реакция |
|---|---|
| Ядро не запустилось или конфиг не прошёл проверку | система не тронута, фаза `error` |
| Туннель не доказан на шаге 5 включения (после одного повтора с новым ядром, 5.3, шаг 5) | ядро остановлено, системный exit node не трогался, фаза `error` |
| Проверка после переключения не прошла | откат 5.4, фаза `error` |
| Ядро упало во время работы | немедленный возврат системного exit node, до трёх попыток перезапуска |
| Сервер VPN недоступен | фаза `degraded`, программы дорожки VPN без связи, DNS через провайдера |
| Путь через адаптер два раза подряд отвечает с адреса прямой дорожки | откат 5.4, фаза `error` (5.5) |
| Путь через адаптер не отвечает при работающем `probe-vpn` | перезапуск ядра: откат 5.4, затем включение 5.3 (5.5) |
| Пользователь включил exit node в системном Tailscale | фаза `blocked` |
| Команда возврата системного exit node не срабатывает | ядро не останавливается, попытки повторяются; через 30 секунд показаны команда для ручного восстановления и действие «Выключить без возврата» (5.4) |
| Окно упало или закрыто | служебный процесс и деление продолжают работать |
| Служебный процесс упал | Ядро продолжает работать без надзора: пока служебного процесса нет, никто не вернёт системный exit node при падении ядра и не заметит фазу `blocked`. Окно при потере канала сразу запускает задачу снова (`schtasks /run`, до 5 попыток с паузой 2 секунды) и показывает плашку «Служебный процесс перезапускается»; если не удалось — «Служебный процесс не отвечает» с действием «Повторить». При старте служебный процесс действует по журналу возврата (5.7): возвращает системный exit node, останавливает оставшееся ядро и включает деление заново, если оно было включено. |
| Файл правил не применился | возвращаются прежние файлы правил и режим (8.3), изменение в окне откатывается, показана ошибка |
| Сон и пробуждение, смена сети | Ядро само сбрасывает соединения. Служебный процесс получает уведомления Windows о питании, об изменении маршрутов и об изменении адаптеров и после события ждёт появления маршрута по умолчанию через подключённый адаптер; пока его нет, ядро не трогает (дорожка VPN закрыта, DNS не переключается): отсутствие сети — не сбой и не повод для отката. Когда сеть появилась, он до 60 секунд ждёт успешных проверок 5.5. Если сеть есть, а проверки не проходят, ядро перезапускается: сначала откат 5.4 (возврат и подтверждение системного exit node), затем включение 5.3. Если после смены сети проверки прошли, а вид соединения встроенного узла с exit node 60 секунд остаётся «через ретранслятор», хотя до события был прямым, ядро тоже перезапускается: узел сам прямое соединение не восстанавливает (приложение A, проверки плана 1B). Перезапуска после смены сети нет в фазе `blocked` (шаг 6 включения выключил бы exit node, выбранный пользователем, 5.7), при истёкшем входе и в фазе `degraded`, начавшейся до события: там действуют обычные правила 5.5. |
| Завершение сеанса Windows при включённом делении | сокращённое выключение (5.4): команда возврата системного exit node отдаётся один раз, ядро завершается без ожидания подтверждения |
| Перезагрузка, отключение питания или сбой Windows при включённом делении | При следующем входе пользователя служебный процесс возвращает системный exit node по журналу (5.7). Если признак «было включено» остался установленным (отключение питания, сбой), деление включается заново; при обычной перезагрузке признак снимается при завершении сеанса (5.4). |

Что система не гарантирует на этапе 1:

- Падение ядра. До возврата системного exit node трафик идёт напрямую (ожидается порядка секунды; в проверке не измерялось, измеряется по ручному списку). Если системного Tailscale нет или exit node в нём не был выбран, весь трафик идёт напрямую до перезапуска ядра, а после трёх неудачных перезапусков — пока пользователь не включит деление снова.
- Остановка ядра самим SplitLane: откат при неудачном включении, перезапуск после смены сети, смена exit node, повторный вход после истечения срока. Для пользователя без exit node в системном Tailscale программы дорожки VPN на это время идут напрямую.
- Служебный процесс завершён, а ядро работает. Пока служебного процесса нет, никто не вернёт системный exit node при падении ядра.
- Перезагрузка, отключение питания или сбой Windows при включённом делении. До следующего входа пользователя exit node в системном Tailscale может оставаться выключенным, и тогда трафик идёт напрямую (5.7).
- Соединения, для которых ядро не определило программу (ICMP, в том числе `ping` и `tracert`; часть коротких обменов UDP; процессы, к которым ядро не получило доступ), идут по основной дорожке. При основной дорожке «Напрямую» это может быть трафик программы из дорожки VPN.
- В фазе `degraded` и в режиме «всё напрямую» имена разрешаются через DNS провайдера (6.4).
- Трафик к частным и локальным адресам и к адресам сети Tailscale всегда идёт напрямую.

Отдельная блокировка на эти случаи вынесена за этап 1.

## 11. Безопасность

- Права администратора есть только у служебного процесса и ядра. Оба запускаются из `%ProgramFiles%\SplitLane\`, куда обычный пользователь писать не может.
- Канал доступен только пользователю, выполнившему настройку, администраторам и SYSTEM. Набор методов закрытый (5.1); ни один метод не принимает путь к файлу для запуска, конфиг ядра или путь для записи.
- Данные от окна проверяются: дорожка из двух значений, правило по видам из 8.2, длины строк ограничены, идентификатор exit node сверяется со списком, а когда списка нет (запасной способ без системного клиента) — с диапазоном адресов сети Tailscale `100.64.0.0/10`.
- Конфиг ядра, файлы правил, ключ встроенного узла и секреты API ядра лежат в каталоге, недоступном обычному пользователю. Пользователю открыт на чтение только подкаталог `export\` с архивами журналов (4.2); эти данные в архив не попадают.
- Локальный API ядра и служба API слушают только `127.0.0.1`, каждый со случайным портом и секретом на каждый запуск; для локального API ограничены источники запросов.
- `tailscale.exe` системного клиента служебный процесс вызывает по полному пути (5.6). Команда `install` сверяет SHA-256 ядра перед копированием (4.3).
- Окно: изоляция контекста включена, удалённое содержимое не загружается, доступ к Node из страницы закрыт, в предзагрузочном скрипте только узкий мост к основному процессу.
- Приложение не содержит серверов, ключей и телеметрии. Внешние запросы: проверка связи и определение внешнего адреса дорожек (сервис `api.ipify.org`), шифрованный DNS `1.1.1.1` через дорожку VPN, обращения встроенного узла к серверам Tailscale (управление и ретрансляторы). Адрес сервиса проверки хранится в `state.json`; по каналу он не передаётся, в интерфейсе этапа 1 его нет.
- Остаточный риск этапа 1: любая программа, запущенная от имени того же пользователя, может отправлять служебному процессу команды из закрытого набора. Проверка вызывающей программы по подписи появится на этапе 2 вместе с установщиком.

Смена основной дорожки и режим «всё напрямую» (включить и вернуть): незакреплённая копия меняет адрес; при основной дорожке «Напрямую» копия, закреплённая за VPN, выходит с адреса VPN; после возврата копия, закреплённая за VPN, снова выходит с адреса VPN, а её соединение, открытое в режиме «всё напрямую», закрыто.
  6. Вложенные правила: папка закреплена напрямую, копия `curl` во вложенной папке — через VPN: копия выходит с адреса VPN.
  7. Контроль утечки: всё время сценария, включая включение и выключение, копия `curl` дорожки VPN раз в 500 мс запрашивает адрес; пока жив процесс ядра и не включён режим «всё напрямую» (шаг 5), ни один ответ не равен адресу прямой дорожки. Запросы, отправленные в режиме «всё напрямую», не учитываются.

## 13. Известные ограничения этапа 1

- Работает только с Tailscale и только на Windows 10/11 x64.
- Нужна учётная запись с правами администратора.
- Рассчитан на одного пользователя Windows. Перехват действует на весь компьютер: программы в других сеансах Windows идут по тем же правилам и основной дорожке, но управлять SplitLane оттуда нельзя.
- Встроенный узел — отдельное устройство в сети Tailscale со своим сроком действия входа.
- DNS общий для обеих дорожек (6.4); в фазе `degraded` и в режиме «всё напрямую» запросы имён всех программ видны провайдеру.
- Если системный Tailscale управляет DNS (`accept-dns` включён, это значение по умолчанию), имена MagicDNS не разрешаются, пока деление включено; если при этом сеть Tailscale переопределяет DNS для всех имён, деление не включается. Проверено только с `accept-dns=false`.
- Трафик WSL и виртуальных машин идёт по основной дорожке.
- Соединения, для которых ядро не определило программу, идут по основной дорожке (раздел 10).
- Программы, которые выходят в сеть через общие системные процессы (например, встроенный веб-компонент Edge), нельзя отделить друг от друга.
- IPv6 в интернет не работает, пока деление включено.
- Нет блокировки на случай падения или остановки ядра (раздел 10).
- Exit node, который выходит в интернет с того же внешнего адреса, что и сам компьютер, не поддерживается: включение завершится с причиной `same_address`.
- Если в системном Tailscale был включён автоматический выбор exit node, после выключения деления будет выбран конкретный узел: в журнале возврата хранится адрес (5.7).
- Сборка не подписана; установщика нет.
